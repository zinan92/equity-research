# Supabase canonical authority

`migrations/202607220001_canonical_authority.sql` is the production application-schema baseline for a new Supabase project. Supabase itself must already provide `auth`, `storage`, and the `anon / authenticated / service_role` roles.

Boundary:

- `market` stores accepted market and point-in-time fundamental records.
- `research` stores accepted documents, broker estimates, and events.
- `control` stores source manifests, ingestion receipts, content-addressed raw object locations, per-run raw captures, accepted/rejected record receipts, and immutable snapshot membership.
- `canonical-raw` is private and accepts only JSON, HTML, and PDF up to 50 MB.
- browser roles receive no schema or table privileges in A2. Only the backend `service_role` can read/write; member/editor policies arrive with F1 and must not expose raw evidence directly.

The SQL migration never alters Supabase-managed `storage.*` tables, triggers, grants, or policies. `storage/canonical-raw.bucket.json` is the desired private bucket contract and must be applied through the Supabase Storage API with a backend service role during deployment. No client policy is created in A2.

The migration is intentionally separate from `product/data_core/migrations/0001_canonical_foundation.postgres.sql`, which remains the earlier M2 parity baseline. New Supabase projects use this migration; migration of legacy rows is an A3 ingestion concern.

`seed.sql` adds one inactive fixture manifest and no market/research facts. It proves development bootstrapping without presenting sample data as production evidence.

Raw object paths are generated by `product/data_core/storage_layout.py`:

```text
canonical-raw/raw/{domain}/{source_key}/{YYYY}/{MM}/{DD}/{hash-prefix}/{sha256}.{json|html|pdf}
```

The same input always yields the same object key. Provider URLs and filenames never determine authority paths.
