# A 股长期投委会 · 产品设计

**日期：** 2026-07-17  
**状态：** Park 已批准产品方向与建议仓位范围；待书面 spec 复核  
**产品阶段：** V1 设计，不包含实现计划

## 1. Outcome Contract

### Intended user outcome

面向可投资资产 1000 万元以上、偏好长期持仓的用户，提供一套统一、可执行、可追溯的 A 股模型组合。用户每周打开产品后，可以直接知道：

1. 当前应该持有哪些股票；
2. 每只股票的目标仓位；
3. 本周应该新建、加仓、持有、减仓还是退出；
4. 相比上周发生了什么变化，以及为什么。

### Success Criteria

1. 首页直接展示市场状态、模型组合、现金仓位、目标仓位和当前动作。
2. 正式组合包含 6–12 只股票，股票与现金仓位合计严格等于 100%。
3. 每条建议保存数据快照、来源、模型版本、生成时间和发布时间，可重复回放。
4. 核心数据过期、缺失、冲突或来源不明时，系统阻断发布，而不是继续生成伪精确建议。
5. 用户可以查看组合表现、历史调仓、个股依据和风险触发条件。
6. Park 可以审核草稿；只有通过审核的版本才能向会员发布。
7. 产品连续四周使用真实数据完成正式发布，且没有不可复现的建议。

### In scope

- A 股；
- 一套统一的长期模型组合；
- 每周正式更新，重大事件临时更新；
- 具体股票名称、目标仓位和买入/持有/减仓动作；
- 个股投资逻辑、估值区间、情景分析和风险触发条件；
- 登录、会员权限、发布历史；
- Park 人工审核和发布；
- Supabase 权威数据库及可审计数据链。

### Out of scope

- 用户资产、持仓和风险问卷输入；
- 个性化组合；
- 港股、美股和其他资产；
- 券商账户连接或自动下单；
- 分钟级交易、日内信号和每日荐股；
- 社区、聊天、排行榜；
- 合规资质设计。Park 已说明合规问题已解决，本 spec 不再评估；相关证据状态为 `Unknown / out of scope`。

### Approved V1 range

- 股票数量：6–12 只；
- 单只目标仓位：5%–15%；
- 单一行业目标仓位：不超过 30%；
- 现金目标仓位：10%–40%；
- 预期持仓周期：6 个月至 3 年；
- 正式节奏：每周一次完整投委会，重大事件触发临时更新。

### V1 investability and liquidity contract

模型组合按 1000 万元基准资金校验可执行性。默认规则由版本化配置管理，任何放宽必须由 Park 批准：

- 排除 ST、`*ST`、退市整理和已知重大退市风险证券；
- 新建仓默认要求上市满 180 个交易日；
- 新建仓默认要求最近 20 个交易日日均成交额不低于 1 亿元；
- 单日计划成交额不得超过该股票最近 20 个交易日日均成交额的 2%；
- 预计完成建仓或减仓不得超过 3 个可交易日；
- 停牌、无有效价格或涨跌停封死时不得假设成交；
- 已持仓股票失去可投资性时进入退出队列，不允许用事后价格假设立即卖出。

## 2. Product definition

V1 是“有发布机制的线上投委会”，不是 UZI 报告展示站、股票终端或量化开发平台。

对会员的核心承诺是：

> 每周给出一套明确的 A 股长期模型组合，并完整记录仓位、变化、依据和风险。

UZI 的 22 维数据、66 位投资者评审和机构模型属于后台分析能力。首页必须收敛为用户可执行的结论，不能把分析复杂度直接倾倒给用户。

## 3. User roles

### Member

- 登录并查看已发布组合；
- 查看本周动作、历史调整、组合表现和个股详情；
- 不能看到草稿或绕过会员权限；
- 不能修改正式组合。

### Park / Publisher

- 查看系统生成的组合草稿和质量状态；
- 查看相对上期的变化和证据；
- 批准、退回或取消发布；
- 发起重大事件临时更新；
- 查看发布、失败和恢复记录。

Park 的批准必须绑定不可变审批包。审批包包含 portfolio、snapshot、model version、相对上期 diff、evidence manifest 和内容哈希。审批后的任何字段变化都会自动撤销批准并退回草稿状态。

### Data service

- 采集、标准化、回填和校验数据；
- 创建不可变数据快照；
- 任何质量 Gate 不通过时 fail closed。

## 4. Information architecture

### 4.1 本周决策

这是登录后的默认首页，按以下顺序展示：

1. **本周总判断**：进攻、均衡或防守；股票总仓位与现金仓位；
2. **本周变化**：新建、加仓、减仓、退出及变化原因；
3. **模型组合**：股票名称、代码、行业、当前价、目标仓位、动作、建议执行区间、置信度；
4. **风险提醒**：最重要的 3 项组合级风险；
5. **数据状态**：数据截止时间、快照 ID、质量状态和发布时间。

首页不展示完整 66 人评审过程。复杂依据通过股票详情中的“证据与分歧”按需展开。

### 4.2 组合与业绩

展示：

- 当前模型组合与目标组合；
- 组合净值及基准；
- 本周、今年以来、成立以来表现；
- 最大回撤、行业暴露和现金变化；
- 个股贡献和拖累；
- 历史换手及估算交易成本；
- 原始发布版本与事后表现严格分离，禁止回写历史建议。

V1 只显示模型组合表现，不接入用户个人账户。

### 4.3 调整记录

使用时间线展示：

- 调整时间和发布类型；
- 股票及仓位前后变化；
- 触发数据或事件；
- 调整原因；
- 调整前后的组合风险；
- 对应快照和发布版本。

### 4.4 股票详情

股票详情从组合与调整记录进入，不占顶层导航。内容包括：

- 核心投资逻辑；
- 财务趋势与数据质量；
- 估值区间；
- Bull / Base / Bear 情景；
- 风险触发条件；
- UZI 深度报告；
- 关键证据、来源与评审分歧。

## 5. Product workflows

### 5.1 Weekly publication

1. 数据服务在周末更新和回填核心数据；
2. 质量 Gate 生成通过或阻断结果；
3. 系统冻结本周数据快照；
4. UZI 生成单股判断和候选池；
5. 组合引擎产生目标仓位和相对上期变化；
6. 发布 Gate 校验仓位、来源、数据新鲜度和解释完整性；
7. Park 审核并批准；
8. 系统创建不可变发布版本，会员可见；
9. 系统从正式发布时间开始计算组合表现。

发布状态机固定为：

```text
draft → quality_passed → approved → published
  ↘ blocked             ↘ invalidated
```

- `quality_passed` 只能由质量 Gate 产生；
- `approved` 必须绑定审批包哈希；
- 审批包发生变化时状态自动变为 `invalidated`；
- 发布使用幂等键和单事务，同一审批包不能重复发布；
- 会员端通过 RLS 只读取 `published` 版本；
- draft、blocked、invalidated 和 approved 均只对 Park 可见。

### 5.2 Major-event update

重大财报、公告、停复牌、监管事件或投资逻辑破坏可触发临时更新。临时更新仍必须：

- 创建新快照；
- 运行同一套质量和仓位 Gate；
- 明确标注相对上一正式版本的变化；
- 由 Park 审核后发布；
- 不覆盖原有版本。

重大事件分为：

- **交易状态**：停复牌、涨跌停无法成交、退市风险；
- **财务披露**：业绩预告、正式财报、重大修订、审计意见；
- **公司行动**：分红、配股、回购、增发、重大资产重组；
- **监管与治理**：立案、处罚、核心管理层变化、重大诉讼；
- **投资逻辑**：订单、产能、竞争格局或关键假设发生实质变化；
- **组合阈值**：估值、风险或仓位漂移触发预设边界。

交易所、巨潮和公司正式披露为优先检测源。事件按证券、事件类型、公告 ID 和内容哈希去重。交易状态与监管类关键事件应在下一个交易时段前完成判断；其他重大事件应在 1 个工作日内进入 Park 审核。若临时更新被质量 Gate 阻断，上一 `published` 版本继续有效，同时后台明确显示待处理事件和阻断原因。

### 5.3 Failure behavior

- 数据源失败：保留原始失败记录，按已批准的 source policy 尝试备用源；
- 所有主备源失败：阻断涉及该字段的正式建议；
- 数据过期：显示 stale 原因并阻断发布；
- 部分股票不合格：组合引擎重新生成，而不是用空值或默认值补足；
- 发布失败：已批准版本保持 draft/approved 状态，不得出现半发布；
- 组合约束失败：整期组合不可发布；
- UZI 与权威数据库结果不一致：以 Supabase 快照为准并记录差异，禁止 UZI 绕过快照重抓核心字段。

### 5.4 Model-portfolio ledger and execution policy

模型组合使用独立、不可回写的账本。初始净值设为 100，正式动作按以下规则计入模拟业绩：

- 周度版本在 Park 发布后，于下一个交易日生效；
- 默认成交价为下一可交易日开盘价，并应用版本化滑点和费用配置；
- 买入使用不利方向滑点，卖出使用不利方向滑点；印花税、佣金等按带生效日期的费用表计算，禁止硬编码永久费率；
- 停牌或涨跌停封死时动作保持 pending，顺延到下一可交易日；5 个交易日仍无法完成则标记 `unfilled`，不得假设成交；
- 上期正式目标、价格漂移后的账面实际权重、本期目标和实际模拟成交必须分别保存；
- 调仓阈值由版本化配置决定，未超过阈值时保持原仓，避免伪精确交易；
- 分红、送转、配股和其他公司行动进入账本并保留来源；
- 基准默认使用沪深 300 全收益口径；若数据源只能提供价格指数，必须明确标记，不得混用；
- 历史收益只能基于当时已发布版本和真实可得价格计算，禁止事后重算为更优结果。

## 6. System boundaries

### 6.1 Integration decision

不物理合并 `datafeed` 和 `quant-data-pipeline` 的 Git 历史，也不让两个旧系统在生产中并行维护各自数据模型。

生产环境只建设一个新的 `data-core`：

- 以 `datafeed` 的 `SourceManifest`、Port、Adapter、provenance、raw response、quality 和 fallback policy 为契约内核；
- 吸收 `quant-data-pipeline` 的 scheduler、backfill、gap detection 和 health check 思路；
- 将 `a-stock-data` 的端点改造成可注册 adapters；
- 向 UZI 暴露统一的研究数据接口；
- 所有标准化数据和发布状态写入 Supabase。

### 6.2 Repository roles

| 资产 | 保留 | 不继承 |
|---|---|---|
| `a-stock-data` | 外部接口、备用源和端点维护经验 | 本地 CSV 缓存作为正式存储 |
| `datafeed` | 数据契约、来源追踪、原始响应和质量策略 | 当前以 K 线为主的薄 A 股模型 |
| `quant-data-pipeline` | 调度、回填、健康检查和运行经验 | SQLite、旧 schema、手工迁移和弱 provenance |
| `UZI-Skill` | 个股研究、估值、投委会判断和组合方法 | 直接实时抓取核心正式数据 |
| Supabase | PostgreSQL、Auth、RLS、Storage、pgvector | 多套并行权威定义 |

## 7. Canonical data model

Supabase 是唯一权威数据平面。逻辑边界如下：

### `market`

- instruments 与名称历史；
- trading_calendar；
- daily_bars_raw；
- adjustment_factors；
- corporate_actions；
- daily_metrics；
- financial_statements 与 financial_indicators；
- industry_membership；
- source_registry、ingestion_runs 和 quality_results。

### `research`

- dataset_snapshots；
- model_runs 与 model_versions；
- stock_assessments；
- portfolio_drafts；
- portfolio_items；
- recommendation_evidence；
- risk_triggers；
- publication_diffs。

每个 `dataset_snapshot` 必须包含不可变 manifest：

- `as_of` 和 `known_at`；
- 原始 payload hash；
- 字段级 source、ingestion run、provider version 和 quality status；
- 财报公告日、修订版本与当时可见性；
- 复权因子和公司行动版本；
- 模型代码版本、配置版本、依赖版本和随机种子；
- manifest 内容哈希。

UZI 正式运行时只能读取指定 snapshot，不得在运行中刷新核心字段。`a-stock-data` adapters 只能写原始采集区，由 `data-core` 标准化和校验后进入正式表。`quant-data-pipeline` 只提供设计模式和可验证逻辑，不成为生产运行依赖。

### `product`

- profiles；
- memberships 与 entitlements；
- publications；
- publication_items；
- read_access 与 audit events。

发布相关记录还必须保存审批包 hash、幂等键、状态迁移历史和模拟组合账本。

### Storage

- 原始 API payload；
- 公告与研报 PDF；
- UZI 报告；
- 发布附件。

数据库备份与 Storage 文件备份必须分别验证。

## 8. Publication Gate

以下任一条件成立时必须阻断发布：

1. 核心行情不是最新已完成交易日；
2. 财务数据缺少公告日期或版本；
3. 复权因子或公司行动不完整；
4. 正式建议依赖来源不明、不可追溯或被标记为低质量的数据；
5. 股票和现金目标仓位之和不等于 100%；
6. 单股、行业或现金仓位超出批准范围；
7. 快照、模型版本或相对上期变化缺失；
8. 组合动作没有可读解释；
9. Park 尚未批准；
10. 发布过程无法保证原子性。
11. 股票池、上市时长、ST/退市风险、停复牌、涨跌停或流动性规则不通过；
12. 预计建仓天数或计划成交额占 ADV 比例超出批准范围；
13. 审批包哈希与待发布内容不一致；
14. 模拟成交和业绩口径所需数据缺失。

质量系统的职责是“允许或禁止发布”，不是只显示警告。

## 9. Testing and evidence

### Data evidence

- 每个标准字段可追踪到 source、ingestion run 和 raw payload；
- 同一 snapshot + model version 重跑结果一致；
- 交易日、复权、财报公告日和历史版本有专项测试；
- 主源失败、备用源成功以及全部源失败均有测试。
- point-in-time 财报修订、复权版本和 `known_at` 可见性有专项测试；
- UZI 运行期间尝试绕过 snapshot 获取核心字段时必须失败。

### Portfolio evidence

- 股票数量、单股仓位、行业仓位、现金仓位和总和均有不变量测试；
- 不合格候选不能进入组合；
- 相同输入产生可复现组合；
- 历史发布不可被回写；
- 基准、交易成本和收益计算口径固定。
- ST/退市、上市时长、停牌、涨跌停、ADV 和预计建仓天数均有不变量测试；
- 下一交易日开盘成交、pending、unfilled、滑点、费用、分红和公司行动有账本测试；
- 审批后内容被修改会撤销批准，重复发布保持幂等。

### Product evidence

- 登录、会员授权、Park 审核、发布和历史访问的端到端证据；
- 本周决策、组合与业绩、调整记录的桌面和移动端截图；
- 一次被质量 Gate 阻断的可视证明；
- 一次完整草稿到发布的可视证明。

日志和命令输出仅作为 trace material，不能代替网页和用户路径的视觉证据。

## 10. Milestones and gates

### M1 · 真实数据基座

**Goal：** 用真实 A 股数据完成外部接口到 Supabase 快照的闭环。  
**Definition of Done：** 股票主表、交易日历、日线、复权、估值、财务及来源追踪可用；质量失败会阻断。  
**Required Evidence：** 至少 12 只跨沪市、深市、创业板、科创板和多个行业的真实样本；覆盖正常交易、停牌、除权、财报修订和历史退市场景；提供完整来源链、数据库记录、质量结果和快照重放。
**Go / No-go：** 不能复现数据时，不进入组合开发。

### M2 · 组合决策引擎

**Goal：** 将 UZI 从单股报告工具升级为受约束的模型组合生成器。  
**Definition of Done：** 输出 6–12 只股票、现金、目标仓位、动作、变化原因和模型版本；流动性、可投资性、仓位和模拟成交约束自动验证。
**Required Evidence：** 两期连续真实组合、仓位和 ADV 不变量测试、相同快照重放、模拟组合账本和完整证据链。
**Go / No-go：** 只能评分但不能形成可解释组合时，不进入产品开发。

### M3 · 完整会员产品

**Goal：** 用户可以登录并使用完整的投委会产品。  
**Definition of Done：** 三个核心页面、股票详情、Auth/RLS、Park 审核和发布流程可用，桌面与移动端通过验证。  
**Required Evidence：** 真实数据页面截图、完整发布流程、权限边界和质量阻断视觉证据。  
**Go / No-go：** 静态 mockup、sample data 或无权限控制不算完成。

### M4 · 四周真实运行

**Goal：** 证明产品可以持续运行，而不是一次性演示。  
**Definition of Done：** 连续四周按时发布，重大事件流程至少验证一次，无不可复现建议，备份恢复通过。  
**Required Evidence：** 四期发布、四个数据快照、发布记录、用户反馈和恢复演练；另用至少一个历史重大事件做确定性 replay，验证触发、去重、阻断、审核和旧版本继续有效。
**Go / No-go：** 连续运行不稳定，不扩大会员规模。

## 11. Rejected approaches

### Physical merge of all repositories

拒绝。它会把不同代码风格、数据模型和历史技术债绑在一起，并使上游更新难以吸收。

### Independent production services for every repository

拒绝。V1 不需要多套独立运行时；这会增加部署、监控、跨服务一致性和 schema 漂移风险。

### Direct external APIs without persistent snapshots

拒绝用于正式发布。可用于补充新闻和实时信息，但任何影响仓位的输入必须进入不可变快照和证据链。

## 12. Decisions

- 产品定位：A 股长期投委会；
- 更新节奏：每周正式更新 + 重大事件临时更新；
- 数据平台：Supabase / PostgreSQL；
- 数据策略：核心落库、补充实时、正式决策全部留快照；
- Repo 策略：逻辑整合，不物理合并；
- 产品导航：本周决策、组合与业绩、调整记录；
- 发布机制：质量 Gate + Park 人工批准；
- V1 不个性化、不自动交易。

## 13. Gotchas

1. “数据源有返回”不等于数据可以发布；必须验证时间、口径、来源和完整性。
2. UZI 现有 fetcher 可能绕过权威快照，迁移期间必须区分正式字段和补充字段。
3. 复权、财报修订、退市股票和行业历史若只保存当前值，会产生未来函数或幸存者偏差。
4. Supabase 数据库备份不自动等于 Storage 文件备份。
5. 组合表现必须从真实发布时间开始计算，不能用事后更新的数据回填历史建议。
6. “产品看起来完整”不能依靠更多页面；完整性来自发布、历史、权限、证据和失败处理闭环。
7. 重大事件更新不能绕过周频流程的质量与人工审核 Gate。
